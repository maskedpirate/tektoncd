# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A local development environment for learning enterprise-style Tekton CI/CD on a `kind` Kubernetes cluster, fronted by Envoy Gateway (Gateway API). It runs Tekton (Pipelines, Triggers, Dashboard) plus a self-hosted Gitea instance that triggers pipelines via webhook — entirely inside the cluster, with no public exposure needed. `init.sh` (the bootstrap script) plus Tekton/Gitea YAML manifests bring up the whole environment from nothing, including seeding Gitea with a sample app, so the environment is reproducible from a wiped cluster with a single command.

## Commands

- Bootstrap/reset the whole environment: `./init.sh` (must be run directly, not sourced — it exits if sourced). It is fully idempotent: safe to re-run any time after editing manifests — it reuses the existing kind cluster/registry/network/Gitea data and just re-applies changed resources.
- Common flags: `-c <cluster-name>` (default `tekton`), `-i <static-ip>` (default `172.24.0.10`), `-s <docker-subnet>` (default `172.24.0.0/16`), `-p/-t/-d` to pin Tekton Pipeline/Triggers/Dashboard versions (default: latest GitHub release of each), `-k` to force Podman instead of Docker.
- Use the cluster afterward with: `export KUBECONFIG="${HOME}/.kube/configs/kind-<cluster-name>.yaml"` (the script writes each cluster's kubeconfig to its own file under `~/.kube/configs/`, not the default `~/.kube/config`).
- Prerequisites: podman or docker, kind, kubectl, helm, jq.
- Trigger the real CI pipeline: push to `main` on the Gitea repo `tekton-lab/hello-world` (`http://gitea.lab.devkit/tekton-lab/hello-world.git`, admin user `gitea_admin`, password in secret `gitea-admin-secret` in namespace `gitea`). That fires an org-level Gitea webhook which runs `hello-world-ci-pipeline` end to end.
- Edit the sample app at `sample-repos/hello-world/` (a Spring Boot Maven project, source of truth in this repo) and push it to Gitea manually to test a change (`init.sh` only seeds the repo once — see below, it won't re-sync edits on its own).
- Run the trivial example manually instead: `kubectl apply -f pipelines/hello-world/ && kubectl create -f pipelines/hello-world/hello-pipelinerun.yaml`.
- Check the local registry's contents: `curl http://localhost:5000/v2/_catalog` and `curl http://localhost:5000/v2/hello-world/tags/list` (port 5000 is published to the host by the `kind-registry` container).

## Architecture

`init.sh` provisions, in order:
1. A container network (`kind`, fixed subnet) and a local image registry (`kind-registry`, port 5000) that the kind cluster is configured to use as a pull-through mirror for `localhost:5000` and `kind-registry:5000` (containerd-level, for pulling images onto nodes — this is separate from how in-cluster pods push to it, see below).
2. A `kind` cluster (1 control-plane + 2 workers) with the control-plane labeled `ingress-ready=yes`.
3. A static alias IP on the control-plane container's `eth0`, reachable directly from the host over the `kind` bridge network, plus an iptables PREROUTING/OUTPUT redirect from port 80 → 10080 inside that container (Envoy's actual hostNetwork listener port).
4. Envoy Gateway (installed via OCI Helm chart), pinned to the `ingress-ready` node, configured with `hostNetwork: true` via an `EnvoyProxy` CRD patch, and wired to a `GatewayClass` named `eg`.
5. A root `Gateway` (`devkit-gateway`, namespace `default`) accepting HTTPRoutes from all namespaces.
6. Tekton Pipelines, Triggers, and Dashboard, installed from `https://infra.tekton.dev/tekton-releases/...` release manifests.
7. An `HTTPRoute` binding hostname `tekton.lab.devkit` to the `tekton-dashboard` service (port 9097) via `devkit-gateway`.
8. A `local-registry` Service+Endpoints in namespace `default` (`local-registry.default.svc.cluster.local:5000`) that manually points at the `kind-registry` container's docker-network IP. This exists because pods resolve names via CoreDNS, not Docker's embedded DNS — a bare single-label name like `kind-registry` fails cluster-DNS resolution (k8s `ndots` search-domain rules never fall through to try it as an external name), so this Endpoints object is what lets kaniko push images from inside a Task pod. Re-applied on every `init.sh` run in case the registry container's IP changes.
9. Gitea (Helm chart from `dl.gitea.com`, values in `gitea/values.yaml`): single pod, sqlite storage, in-memory cache/session/queue (deliberately lightweight — not for production). Exposed at `http://gitea.lab.devkit` via `gitea/httproute.yaml`. Admin credentials are generated once into secret `gitea-admin-secret` (namespace `gitea`) and mirrored into secret `gitea-credentials` (namespace `default`) so Tekton Task workspaces there can use them (Secrets don't cross namespaces). Config sets `webhook.ALLOWED_HOST_LIST: "*"`, which is required — by default Gitea blocks webhook deliveries to internal/private hostnames as an SSRF guard, and the whole point here is that Gitea calls the EventListener's in-cluster address.
10. The Tekton Triggers wiring (`triggers/rbac.yaml`, `triggers/gitea-trigger.yaml`, namespace `default`): a `TriggerBinding`/`TriggerTemplate`/`EventListener` (`gitea-listener`) that filters incoming webhooks with the **CEL** interceptor on `header.match('X-Gitea-Event', 'push')`. There is no dedicated Tekton "gitea" interceptor (only github/gitlab/bitbucket/slack/cel ship with Triggers), and Gitea's `X-Gitea-Signature` HMAC header isn't compatible with the `github` interceptor's verifier, so **no HMAC signature validation is configured** — acceptable only because the EventListener is never exposed outside the cluster network.
11. `pipelines/hello-world/`: the original trivial example (`Task`/`Pipeline`/`PipelineRun` that just echoes a string) — left in place as a minimal manual-apply reference, no longer wired to the trigger.
12. `pipelines/hello-world-ci/`: the real pipeline the Gitea webhook triggers. `hello-world-ci-pipeline` chains four Tasks: `git-clone` (auth'd via the `git-credentials` workspace, since this Gitea instance requires sign-in even for repos marked non-private) → `maven-build` (`mvn -DskipTests package`, produces the jar once) → `maven-test` (`mvn test`, reuses the jar-bearing workspace) → `kaniko-build-push` (builds the `Dockerfile` from the hello-world repo and pushes to `local-registry.default.svc.cluster.local:5000/hello-world:<git-sha>` with `--insecure`, since that registry is plain HTTP). One shared `source` PVC workspace carries the checkout and build output across all four Task pods (works cleanly with the `local-path` provisioner because it schedules Task pods onto whichever node holds the PVC).
13. Gitea org/repo/webhook bootstrap via the Gitea REST API (`curl`+`jq`, idempotent by checking for existing org/repo/webhook first): org `tekton-lab`, repo `hello-world`, and an **org-level** webhook (fires for any future repo in the org, not just this one) pointed at `http://el-gitea-listener.default.svc.cluster.local:8080/`.
14. Seeding: `sample-repos/hello-world/` in this repo is the checked-in source of truth for the sample app. `init.sh` checks whether `pom.xml` already exists in the Gitea repo (via the contents API) and, if not, does a one-off `git init`/commit/merge-with-the-auto-init-README/push into a temp dir to publish it — so a wiped Gitea repo (or a wiped cluster) comes back with the working sample app already there, not just an empty README. This check only looks for that one file's presence, so it seeds once and never overwrites later commits — editing `sample-repos/hello-world/` after the repo has already been seeded requires either pushing manually or deleting the Gitea repo (`DELETE /api/v1/repos/tekton-lab/hello-world`) and rerunning `init.sh` to reseed.

For the dashboard/Gitea hostnames to resolve, local DNS (dnsmasq) must map `*.lab.devkit` → the control-plane static IP (the script prints the exact line to add: `address=/devkit/<static-ip>`); this has already been confirmed working both from the host and from inside pods (CoreDNS forwards it upstream successfully) in this environment.

GHCR publishing (pushing images to `ghcr.io` in addition to the local registry) is a planned but not-yet-wired follow-up — it needs a GitHub PAT with `write:packages` supplied out-of-band (never commit it), which would be stored as a separate `kubernetes.io/dockerconfigjson` Secret and consumed by an additional Task/step, since the current `kaniko-build-push` Task has no registry auth at all (the local registry needs none).
