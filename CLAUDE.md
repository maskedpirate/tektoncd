# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A local development environment for learning enterprise-style Tekton CI/CD on a `kind` Kubernetes cluster, fronted by Envoy Gateway (Gateway API). It runs Tekton (Pipelines, Triggers, Dashboard) plus a self-hosted Gitea instance that triggers pipelines via webhook — entirely inside the cluster, with no public exposure needed. `init.sh` (the bootstrap script) plus Tekton/Gitea YAML manifests bring up the whole environment from nothing, including seeding Gitea with a sample app, so the environment is reproducible from a wiped cluster with a single command.

## Commands

- Bootstrap/reset the whole environment: `./init.sh` (must be run directly, not sourced — it exits if sourced). It is fully idempotent: safe to re-run any time after editing manifests — it reuses the existing kind cluster/registry/network/Gitea data and just re-applies changed resources.
- Common flags: `-c <cluster-name>` (default `tekton`), `-i <static-ip>` (default `172.24.0.10`), `-s <docker-subnet>` (default `172.24.0.0/16`), `-p/-t/-d` to pin Tekton Pipeline/Triggers/Dashboard versions (default: latest GitHub release of each), `-k` to force Podman instead of Docker.
- Use the cluster afterward with: `export KUBECONFIG="${HOME}/.kube/configs/kind-<cluster-name>.yaml"` (the script writes each cluster's kubeconfig to its own file under `~/.kube/configs/`, not the default `~/.kube/config`).
- Prerequisites: podman or docker, kind, kubectl, helm, jq, envsubst (gettext).
- Browse the registry visually at `http://registry.lab.devkit` instead of curling the API directly.
- Trigger the real CI pipeline: push to `main` on the Gitea repo `tekton-lab/hello-world` (`http://gitea.lab.devkit/tekton-lab/hello-world.git`, admin user `gitea_admin`, password in secret `gitea-admin-secret` in namespace `gitea`). That fires an org-level Gitea webhook which runs `hello-world-ci-pipeline` end to end.
- Edit the sample app at `sample-repos/hello-world/` (a Spring Boot Maven project, source of truth in this repo) and push it to Gitea manually to test a change (`init.sh` only seeds the repo once — see below, it won't re-sync edits on its own).
- Run the trivial example manually instead: `kubectl apply -f pipelines/hello-world/ && kubectl create -f pipelines/hello-world/hello-pipelinerun.yaml`.
- Check the local registry's contents: `curl http://localhost:5000/v2/_catalog` and `curl http://localhost:5000/v2/hello-world/tags/list` (port 5000 is published to the host by the `kind-registry` container).

## Architecture

`init.sh` is a thin orchestrator: it parses flags, sets defaults, sources `lib/*.sh`, and calls one function per stage in order. Each stage function is idempotent, and each lib file owns one concern:

| lib file | stage functions | what it does |
|---|---|---|
| `lib/common.sh` | `info`, `get_latest_release`, `print_summary` | shared helpers, no state of its own |
| `lib/kind.sh` | `setup_network`, `setup_registry_container`, `setup_kind_cluster`, `setup_static_ip_and_nat` | docker network, `kind-registry` container, the kind cluster itself, and the control-plane's static IP + iptables NAT redirect |
| `lib/envoy.sh` | `setup_envoy_gateway`, `wait_for_envoy_dataplane` | Envoy Gateway Helm install + `envoy/*.yaml` (EnvoyProxy/GatewayClass/Gateway) |
| `lib/tekton.sh` | `setup_tekton` | Tekton Pipelines/Triggers/Dashboard install + `tekton/httproute.yaml` |
| `lib/registry.sh` | `bridge_local_registry`, `deploy_registry_ui` | bridges the registry container into the cluster, deploys the registry UI |
| `lib/gitea.sh` | `setup_gitea` | Gitea Helm install, admin secret, credential mirroring, HTTPRoute |
| `lib/ci.sh` | `apply_ci_pipelines`, `bootstrap_gitea_repo` | applies the Task/Pipeline/Trigger manifests, bootstraps org/repo/seed/webhook |

Static manifests live as plain files next to the concern they belong to (`envoy/`, `tekton/`, `gitea/`, `registry-ui/`, `triggers/`, `pipelines/`) and are applied with `kubectl apply -f`. Exactly one manifest has a genuinely dynamic value — `registry/local-registry.yaml.tmpl`, templated with `envsubst` for `$REGISTRY_IP` (discovered via `docker inspect` at runtime, since it can change whenever the registry container is recreated) — everything else needed no templating once extracted, since their "dynamic-looking" values (hostnames, node selectors) were actually just static literals inlined in what used to be one large script.

What each stage actually provisions, in order:
1. **`setup_network` / `setup_registry_container`**: a container network (`kind`, fixed subnet) and a local image registry (`kind-registry`, port 5000) that the kind cluster is configured to use as a pull-through mirror for `localhost:5000` and `kind-registry:5000` (containerd-level, for pulling images onto nodes — separate from how in-cluster pods push to it, see #8).
2. **`setup_kind_cluster`**: a `kind` cluster (1 control-plane + 2 workers) with the control-plane labeled `ingress-ready=yes`.
3. **`setup_static_ip_and_nat`**: a static alias IP on the control-plane container's `eth0`, reachable directly from the host over the `kind` bridge network, plus an iptables PREROUTING/OUTPUT redirect from port 80 → 10080 inside that container (Envoy's actual hostNetwork listener port).
4. **`setup_envoy_gateway`**: Envoy Gateway (OCI Helm chart, values in `envoy/values.yaml`), pinned to the `ingress-ready` node, configured with `hostNetwork: true` via the `EnvoyProxy` CRD in `envoy/envoyproxy.yaml`, wired to `GatewayClass` `eg`, with a root `Gateway` (`envoy/gateway.yaml`, `devkit-gateway`, namespace `default`) accepting HTTPRoutes from all namespaces.
5. **`setup_tekton`**: Tekton Pipelines, Triggers, and Dashboard from `https://infra.tekton.dev/tekton-releases/...` release manifests, plus `tekton/httproute.yaml` binding `tekton.lab.devkit` to the dashboard service (port 9097).
6. **`bridge_local_registry`**: a `local-registry` Service+Endpoints in namespace `default` (`local-registry.default.svc.cluster.local:5000`) that manually points at the `kind-registry` container's docker-network IP. This exists because pods resolve names via CoreDNS, not Docker's embedded DNS — a bare single-label name like `kind-registry` fails cluster-DNS resolution (k8s `ndots` search-domain rules never fall through to try it as an external name), so this Endpoints object is what lets the buildah Task push images from inside a Task pod. Re-applied on every `init.sh` run in case the registry container's IP changes.
7. **`deploy_registry_ui`**: `joxit/docker-registry-ui` as a Deployment+Service in namespace `default`, exposed at `registry.lab.devkit`. Its bundled nginx proxies `/v2/*` server-side to `local-registry.default.svc.cluster.local:5000`, so the browser never needs CORS. `REGISTRY_STORAGE_DELETE_ENABLED=true` is set on the registry container so the UI's delete button works (only takes effect on a freshly-created registry container, not one already running).
8. **`setup_gitea`**: Gitea (Helm chart from `dl.gitea.com`, values in `gitea/values.yaml`): single pod, sqlite storage, in-memory cache/session/queue (deliberately lightweight — not for production). Exposed at `http://gitea.lab.devkit` via `gitea/httproute.yaml`. Admin credentials are generated once into secret `gitea-admin-secret` (namespace `gitea`) and mirrored into secret `gitea-credentials` (namespace `default`) so Tekton Task workspaces there can use them (Secrets don't cross namespaces). Config sets `webhook.ALLOWED_HOST_LIST: "*"`, which is required — by default Gitea blocks webhook deliveries to internal/private hostnames as an SSRF guard, and the whole point here is that Gitea calls the EventListener's in-cluster address.
9. **`apply_ci_pipelines`**: `pipelines/hello-world/` (the original trivial `Task`/`Pipeline`/`PipelineRun` example, no longer wired to the trigger) plus `pipelines/hello-world-ci/`, the real pipeline the Gitea webhook triggers. Its three Tasks (`task-git-clone.yaml`, `task-maven.yaml`, `task-buildah.yaml`) are **vendored, pinned copies of the actual Tekton catalog Tasks** (`tektoncd/catalog`, not hand-rolled) — deliberately vendored as plain files rather than fetched at run time via the Hub resolver (`resolver: hub`), to keep this reproducible without a runtime dependency on hub.tekton.dev, consistent with how Tekton's own release manifests are already pulled from a fixed URL rather than "latest". Each file's header comment records its exact source URL/version and what's overridden. `hello-world-ci-pipeline` chains: `git-clone` (catalog Task; auth via its `basic-auth` workspace, bound to the `git-credentials` Secret containing literal `.git-credentials`/`.gitconfig` files — git's own credential-store format, built by `lib/gitea.sh` — since this Gitea instance requires sign-in even for repos marked non-private) → `maven` invoked twice, once per Pipeline step (`build`: `GOALS: ["-DskipTests", "clean", "package"]`; `test`: `GOALS: ["test"]`) sharing an `.m2` cache via a `subPath` on the `source` workspace — reusing one parameterized catalog Task for two Pipeline steps rather than writing two near-identical Tasks is the standard pattern → `buildah` (catalog Task; replaces kaniko, which Google archived) builds the `Dockerfile` from the hello-world repo and pushes to `local-registry.default.svc.cluster.local:5000/hello-world:<git-sha>` with `TLSVERIFY: "false"`, since that registry is plain HTTP — buildah's underlying `containers/image` library tries HTTPS first and falls back to plain HTTP on a failed TLS handshake, which has the same effect as kaniko's old explicit `--insecure` flag. Unlike kaniko, buildah does real image builds/mounts under the hood and so runs with `privileged: true` — acceptable on a stock `kind` cluster since nothing here restricts Pod Security. One of the three catalog Tasks' own defaults would have silently broken this pipeline if left alone, so the Pipeline overrides it explicitly: `maven`'s `MAVEN_IMAGE` default (`gcr.io/cloud-builders/mvn`, a years-old image with an unknown/old JDK) → `maven:3.9.9-eclipse-temurin-21`. One shared `source` PVC workspace carries the checkout and build output across all Task pods (works cleanly with the `local-path` provisioner because it schedules Task pods onto whichever node holds the PVC); `maven-settings` is a separate `emptyDir` workspace (bound at the PipelineRun level in the TriggerTemplate — a raw `emptyDir` binding is only valid there or on a TaskRun, not inline in a Pipeline's per-task workspace list). This same function also applies `triggers/rbac.yaml` and `triggers/gitea-trigger.yaml`: a `TriggerBinding`/`TriggerTemplate`/`EventListener` (`gitea-listener`) that filters incoming webhooks with the **CEL** interceptor on `header.match('X-Gitea-Event', 'push')`. There is no dedicated Tekton "gitea" interceptor (only github/gitlab/bitbucket/slack/cel ship with Triggers), and Gitea's `X-Gitea-Signature` HMAC header isn't compatible with the `github` interceptor's verifier, so **no HMAC signature validation is configured** — acceptable only because the EventListener is never exposed outside the cluster network.
10. **`bootstrap_gitea_repo`**: org/repo/webhook bootstrap via the Gitea REST API (`curl`+`jq`, idempotent by checking for existing org/repo/webhook first): org `tekton-lab`, repo `hello-world`, and an **org-level** webhook (fires for any future repo in the org, not just this one) pointed at `http://el-gitea-listener.default.svc.cluster.local:8080/`. The same function seeds the repo: `sample-repos/hello-world/` in this repo is the checked-in source of truth for the sample app, and `init.sh` checks whether `pom.xml` already exists in the Gitea repo (via the contents API) — if not, it does a one-off `git init`/commit/merge-with-the-auto-init-README/push from a temp dir to publish it, so a wiped Gitea repo (or a wiped cluster) comes back with the working sample app already there, not just an empty README. This check only looks for that one file's presence, so it seeds once and never overwrites later commits — editing `sample-repos/hello-world/` after the repo has already been seeded requires either pushing manually or deleting the Gitea repo (`DELETE /api/v1/repos/tekton-lab/hello-world`) and rerunning `init.sh` to reseed.

This whole sequence has been verified end-to-end from an absolute cold start more than once (`kind delete cluster` + remove the `kind-registry` container + remove the `kind` docker network, then a single `./init.sh`) — it rebuilds everything and the resulting seed push fires the webhook and runs `hello-world-ci-pipeline` to success unattended.

For the dashboard/Gitea hostnames to resolve, local DNS (dnsmasq) must map `*.lab.devkit` → the control-plane static IP (the script prints the exact line to add: `address=/devkit/<static-ip>`); this has already been confirmed working both from the host and from inside pods (CoreDNS forwards it upstream successfully) in this environment.

GHCR publishing (pushing images to `ghcr.io` in addition to the local registry) is a planned but not-yet-wired follow-up — it needs a GitHub PAT with `write:packages` supplied out-of-band (never commit it), which would be stored as a separate `kubernetes.io/dockerconfigjson` Secret and consumed by an additional Task/step, since the current `buildah` Task invocation has no registry auth at all (the local registry needs none).
